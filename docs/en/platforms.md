# Cross-platform thin-host constraints

> English | [简体中文](../zh-CN/platforms.md)

- The document application ships with the CAF container. The web and Tauri native hosts only handle files, metadata, the bookshelf, storage, export, and the restricted bridge; in-book business logic must not be copied into the platform layer, and the document's original bytes must not be modified.
- The single entry point of the platform interface is `web/platform.js`. The web side keeps the static catalog, file picking, and the existing personal storage; the native side adapts to the system file picker, the app-private bookshelf, and JSON persistence. CAF content and installers are kept separate; packaging copies only host files, and `web/books/`, PDFs, corpora, or user records must never be packed into the program.
- Native import copies in chunks and de-duplicates by file SHA-256; bookshelf metadata is written only after the Worker verifies successfully. The document-reading protocol is hash-addressed, supports range requests, and rejects arbitrary paths; the whole document must not be shuttled back and forth over JSON IPC. WebViews without JSPI still have the whole-file in-memory fallback, and the limitation must be stated honestly.
- Keep the iframe sandbox and a separate CSP; native session tokens are injected only into the top-level page. No in-book code may ever gain direct filesystem or syscall capability. User records are isolated by CAF root hash, written with bounded keys, and replaced atomically; no server, login, or database is introduced.
- Disk paths, Android content URIs, and iOS security-scoped file URLs are all supported, covering both cold start and open-while-running. Desktop packages follow the platform naming conventions; the UI keeps Simplified Chinese. Every newly opened file still goes through full CAF verification — extension or header checks are never a substitute.
- CI keeps only `Reader Release`, independently building the unsigned release artifacts for Windows x64, Ubuntu x64, and Android ARM64, collecting them into a draft for manual publication; the Android APK must be signed separately before installation. There are no iOS or macOS CI builds; local build entry points remain. When a target system, SDK, or physical device was unavailable, that is recorded as unverified — never claim to have built or published it.
- Acceptance uses small standalone fixtures covering native runs, WASM, resource Range, sandbox/network/native-permission denial, personal-data persistence across app restarts, plus web open/close, bookshelf, and storage-isolation regression. Build commands are in the README's build-and-run section.
